**GigaAM-v3 бьёт Whisper примерно втрое по ошибкам и в ~20 раз быстрее на CPU** (RTF 0.047 против 1.02) — https://habr.com/ru/articles/1042574/ . Та же статья: AGC/VAD-обрезка перед распознаванием **ухудшает** WER на 6–9 п.п. — не предобрабатывать голосовые из Telegram.

**A (рекомендация): GigaAM-v3 e2e_rnnt на CPU через ONNX.** 220–240M параметров, **MIT**, e2e даёт пунктуацию и нормализацию чисел. CPU 0.66 с на запрос, **0 ГБ VRAM**. Готовые серверы: `oaitt` (https://github.com/haiodo/oaitt) — **OpenAI-совместимый `/v1/audio/transcriptions`**, drop-in вместо Groq; `gigastt` (https://github.com/ekhodzitsky/gigastt) — REST `/v1/transcribe`, Docker CPU/CUDA; `onnx-asr` + веса `istupakov/gigaam-v3-onnx`. Грабли: вход строго float32 (int16 → пустая строка без ошибки); warmup — первые вызовы в 3–5 раз медленнее; для 10–60 с не чанковать. Telegram даёт OGG/Opus 48 кГц → ffmpeg → wav 16 кГц mono float32.

**B: faster-whisper large-v3-turbo через Speaches** (https://github.com/speaches-ai/speaches) — OpenAI-совместимый, образы cuda/cpu. VRAM: large-v3 INT8 ~3 ГБ, turbo INT8 ~1.6 ГБ; на CPU 1 час аудио за ~6 мин. MIT. Нулевая переделка (тот же формат, что у Groq), но WER в 2–3 раза хуже GigaAM.

**C: Yandex SpeechKit** — 0.1626 ₽ за 15 с (≈0.65 ₽/мин), https://aistudio.yandex.ru/docs/ru/speechkit/pricing.html . Данные в РФ, но это поручение обработки третьему лицу — нужен договор.

## 2. Vision: хватает встроенного зрения основной модели

- Qwen3.8-27B — нативная VLM, Apache 2.0; на Q4_K_M даёт точные bounding boxes и детальные описания (https://simonwillison.net/2026/Aug/16/qwen-38-27b/); Qwen3.5+ по vision-бенчмаркам обходит отдельную линейку Qwen3-VL.
- Gemma 4 31B лидирует на MMMU Pro (76.9 %); бюджет визуальных токенов настраивается (70…1120, по умолчанию 280).
- **Бенчмарков «фото еды → блюдо + порция» для этих моделей нет.** Оценка порции по фото — задача, где и Claude ошибается; от 27B точнее ±30 % по граммовке ждать не стоит. Практика: модель выдаёт название блюда + компоненты + «маленькая/средняя/большая порция», а граммы и КБЖУ считаются через `lookup_food`.
- **Вывод: отдельная VLM не нужна** — экономия 4–8 ГБ VRAM.

**Как обслуживаются картинки.** vLLM: префикс-кэш работает и с изображениями; `--limit-mm-per-prompt image=N`; `mm_processor_cache_gb` по умолчанию 4 ГиБ — **на 24 ГБ уменьшить до 1–2**. Для Qwen-VL токенов ≈ H×W/1024: 896×896 → 784 токена; «пачка до 5 фото» ≈ 4 000 токенов. llama.cpp: нужен `--mmproj`; каждая картинка 1000+ KV-токенов; открыт баг OOM при кэшировании мультимодальных промптов (https://github.com/ggml-org/llama.cpp/issues/22629).

## 3. Чтение PDF/DOCX

Ключевое: **у универсальных парсеров кириллица не включена по умолчанию** — Docling issue #3433 (открыт с мая 2026), в docling-serve `ocr_lang` иногда игнорируется (issue #567). Русский OCR настраивать руками и проверять.

| Вариант | Что умеет | VRAM/CPU | Лицензия | API |
|---|---|---|---|---|
| **A. Docling-serve + Tesseract rus** (или RapidOCR cyrillic) | PDF/DOCX/PPTX/XLSX → Markdown/JSON, таблицы, layout | CPU-образ работает; на GPU 4–6 ГБ/worker | MIT | `quay.io/docling-project/docling-serve`, `/v1/convert/file` |
| **B. PyMuPDF + PaddleOCR PP-OCRv5 cyrillic / RapidOCR** | текстовый слой через PyMuPDF, сканы через OCR | CPU (ONNX), сотни МБ RAM | Apache 2.0 (PaddleOCR); PyMuPDF — AGPL (или pypdfium2) | свой FastAPI |
| **C. Основная LLM по страницам-картинкам** | рендер 150 dpi → Qwen3.8 «перепиши таблицу анализов в JSON» | 0 доп. VRAM, ~800–1500 токенов/стр., медленно | — | уже есть эндпоинт vLLM |
| Marker v2 / MinerU | лучший layout (76.0 / 72.7 балла), 3–5 / 6–8 ГБ VRAM | тяжёлые | Marker — ограничения на коммерцию; MinerU AGPL | FastAPI-обёртки |
| olmOCR-2 / Nanonets-OCR2 | VLM-OCR 3–7B, 16–32 ГБ | дорого рядом с 27B | Apache 2.0 | — |

**Рекомендация — гибридный маршрут:** PyMuPDF/pdfplumber проверяет текстовый слой → есть — текст в LLM; скан → Docling-serve (CPU, Tesseract `rus+eng`) → Markdown; мусор (низкая доля кириллицы) → фолбэк C: страница картинкой в Qwen3.8. DOCX — через Docling или уже стоящий Gotenberg → PDF. Справка/анализы 1–5 страниц ≈ 2–8k токенов — целиком; длинные документы — по разделам в цикле.

## 4. Веб-поиск

**A (рекомендация): Yandex Search API** — 488 ₽ / 1000 синхронных запросов днём, 366 ночью; отложенные 30.5 ₽/1000; «генеративный ответ» 5 080 ₽/1000 (https://aistudio.yandex.ru/docs/ru/search-api/pricing.html). Российский контур, HTTP Request без библиотек. 1 000 запросов/мес ≈ 500 ₽.

**B: SearXNG self-hosted** — Google на self-hosted отдаёт 403/CAPTCHA; стабильно `duckduckgo,bing` с паузой ≥3 с. **Доступность DDG/Bing с российских IP в 2026 не подтверждена.** Есть движок `yandex_api` (нужны api_key + folder_id) — можно объединить A и B.

**C: fetch страниц + локальная суммаризация** — Crawl4AI (Docker ~2 ГБ, Apache 2.0, HTTP API) или Firecrawl self-hosted (AGPL); текст до ~3k токенов/страница → Qwen3.8 на суммаризацию; наш подчинённый workflow веб-поиска меняет только источник текста.

**Зарубежный поиск только с текстом запроса?** Трансграничная передача — это передача ПДн; запрос «норма белка при похудении» ПДн не содержит. Но оператор обязан гарантировать, что в запрос не просочились имя/возраст/диагноз (здоровье — специальная категория), а факт обращения остаётся в логах провайдера. Юристы советуют считать любой промпт с ПДн трансграничной передачей (https://mypl.pro/audit-ii/zakony/152-fz-i-obuchenie-modeley , https://b-152.ru/chto-schitat-transgranichnoj-peredachej-pdn). Если оставлять зарубежные движки — детерминированный «скруббер» запроса + логирование. Для продукта «все данные в РФ» безопаснее A.

## 5. Инференс-сервер и n8n

### Память под 24 ГБ (цифры из практики)

| Конфигурация | Веса | KV / контекст | Источник |
|---|---|---|---|
| Qwen3.8-27B AWQ, vLLM, RTX 4090 | ~15.5 ГБ | автор ставит `--max-model-len 4096`, «выше 6K возможен OOM» — консервативно | https://makeronsite.com/blog/2026/08/067-qwen38-27b-rtx4090-deployment-en/ |
| Qwen3.8-27B W4A16 AutoRound (vLLM с патчами, RTX 3090 24 ГБ) | ~19.5 ГБ | 57k токенов (bf16 KV), до 150k с int8 KV; vision `VISION=1`; tool calling `qwen3_coder` работает; ~114 т/с single, ~1000 т/с на 64 параллельных | https://github.com/syv-ai/qwen38-27b-rtx3090 |
| Qwen3.8-27B FP8 офиц. | 14.28 ГиБ | линейное внимание на 48 из 64 слоёв — «полные 262k ≈ 17 ГБ» | https://recipes.vllm.ai/Qwen/Qwen3.8-27B |
| Qwen3.8-27B NVFP4 | 10.6–12 ГиБ | на RTX 5090 требует `--enforce-eager`; на Ada FP4 не нативный | |
| Gemma 4 31B NVFP4 | 16–21 ГБ | «короткий контекст — 24 ГБ, 256K — 32 ГБ; на одной 4090 возможен OOM» | https://blog.pebblous.ai/story/google-gemma-4-nvfp4-report-pb/en/ |

**Вывод по модели: Qwen3.8-27B.** (1) Гибридное внимание — KV в разы дешевле Gemma 4, на 24 ГБ реально 32–64k контекста с параллельными сессиями; (2) Apache 2.0; (3) tool calling через `qwen3_coder` стабилен, а у Gemma 4 в vLLM **открыт баг**: при reasoning теги утекают в чат, без reasoning tool calls утекают в текст (https://github.com/vllm-project/vllm/issues/39043). Gemma 4 на 48 ГБ — как эксперимент, не основа.

**Критическая грабля Qwen3.8:** по умолчанию `reasoning_effort=xhigh` — простые задачи в 10 раз дольше; на 5090 ответ 1.44 с → 0.21 с при off, генерация 73 → 151 т/с (https://huggingface.co/Qwen/Qwen3.8-27B/discussions/113). Для бота `enable_thinking: false`, для `/research` — `low`. Глобально: `--default-chat-template-kwargs '{"enable_thinking": false}'`, либо per-request через Extra Body в n8n.

### Сервер

| | vLLM | SGLang | llama.cpp server | Ollama |
|---|---|---|---|---|
| Tool calling | `--enable-auto-tool-choice --tool-call-parser qwen3_coder` / `gemma4`; `--reasoning-parser qwen3` | аналогично | jinja-шаблон, парсеры менее зрелые | есть, нет управления reasoning |
| Structured output | `response_format: json_schema` (xgrammar) | да | GBNF | частично |
| Префикс-кэш | автоматический, хэш по блокам, картинки тоже | RadixAttention, ~29 % быстрее на префиксных нагрузках | `cache_prompt` по слотам | как llama.cpp |
| Параллельность | continuous batching | то же | `--parallel N`, KV делится | ограниченно |
| Квантование | AWQ, GPTQ, FP8, NVFP4 | AWQ/FP8 | GGUF | GGUF |
| Vision | нативно | нативно | `--mmproj`, баг OOM | да |
| 24/7 | зрелый; резервирует ~90 % VRAM — на 24 ГБ настраивать | быстро меняется | простой | не для многопользовательского |

**Рекомендация: vLLM.** Стартовая команда для 24 ГБ:

```
vllm serve <Qwen3.8-27B-AWQ или W4A16> \
  --max-model-len 32768 --gpu-memory-utilization 0.92 \
  --kv-cache-dtype fp8 --enable-prefix-caching \
  --reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder \
  --limit-mm-per-prompt '{"image":5}' --mm-processor-cache-gb 1 \
  --default-chat-template-kwargs '{"enable_thinking": false}'
```
`--max-model-len` подбирать по факту (57k у syv-ai против 4k у MakerOnSite — зависит от квантованных весов).

### Подключение к n8n
- Узел **OpenAI Chat Model** → credential с **Base URL** `http://vllm:8000/v1`, ключ любой; из Docker — имя сервиса. Имя модели — как отдаёт `/v1/models`.
- **AI Agent + инструменты работает**: n8n шлёт стандартный `tools[]`, vLLM возвращает `tool_calls`. `reasoning_content` обёртка отбрасывает — плюс.
- Доп. параметры (`chat_template_kwargs`, `reasoning_effort`) — **Options → Extra Body** (подтверждено на n8n 2.35.6).
- Узел **OpenAI (обычный)** Base URL не поддерживает (n8n issue #12608) — для vision/PDF вне агента — HTTP Request.
- Готового compose «n8n + vLLM + whisper» нет; ближайшее — https://github.com/hwdsl2/self-hosted-ai-stack (Ollama, LiteLLM, Whisper, Docling). Собирать свой: `vllm/vllm-openai`, `oaitt`/`speaches`, `docling-serve`, `searxng`, `crawl4ai`, n8n + Postgres + Gotenberg.

## Итог: что выбрать

| Блок | 24 ГБ (RTX 4090/5090) | 48 ГБ (L40S) |
|---|---|---|
| **LLM + vision** | Qwen3.8-27B AWQ/W4A16, vLLM, 16–32k ctx, thinking off | Qwen3.8-27B FP8 (14.3 ГиБ), 64–128k ctx |
| **ASR** | GigaAM-v3 e2e_rnnt на CPU (oaitt), 0 VRAM | то же, либо GPU 1–2 ГБ; Whisper turbo INT8 фолбэк для англ. |
| **PDF/DOCX** | Docling-serve CPU + Tesseract rus; фолбэк — страница картинкой в Qwen | Docling GPU worker 4–6 ГБ |
| **Поиск** | Yandex Search API (~0.5 ₽/запрос) + Crawl4AI | то же |
| **Итого VRAM** | 19.5 ГБ веса + 3–4 ГБ KV/mm-cache ≈ **23 ГБ** — впритык | 30–40 ГБ, запас |
| **CPU/RAM** | 8+ ядер, 32 ГБ RAM (GigaAM 1–2 ГБ, Docling 4–8 ГБ, Crawl4AI 1–2 ГБ, Postgres, n8n) | то же |

На 24 ГБ узкое место — **параллельность**: 3–4 одновременных диалога по 12k токенов заполняют остаток. Для фокус-группы хватит; для 50+ активных — 48 ГБ.

## Что переписать в workflow

1. **Голос**: Groq → HTTP Request на `oaitt` (`/v1/audio/transcriptions`, тот же multipart). Конвертация OGG→WAV 16k float32 — в контейнере ASR (в Code-ноде `require` запрещён). Алерт голоса перенацелить.
2. **Vision**: Claude с `passthroughBinaryImages` → OpenAI Chat Model (Base URL vLLM); лимит `image=5` под пачки. Промпт еды — «компоненты + размер порции», КБЖУ через `lookup_food`. Визуальный safety-гейт перепроверить на Qwen.
3. **Документы**: нативный PDF-блок Claude исчезает → ветка: файл → проверка текстового слоя → Docling `/v1/convert/file` → при провале страницы в PNG → Qwen → склейка → в агент текстом. Фильтр инъекций — детерминированно перед подачей.
4. **Веб-поиск**: серверный `web_search` → Yandex Search API → top-5 → Crawl4AI → обрезка → суммаризация Qwen (`low`). «Opus в поиске / Sonnet в агенте» → одна модель. PubMed E-utilities — зарубежный API NCBI, без ПДн допустим при скруббере.
5. **Агент и инструменты**: Anthropic Chat Model → OpenAI Chat Model с Base URL; Extra Body `{"chat_template_kwargs":{"enable_thinking":false}}`; 20 инструментов протестировать на `qwen3_coder` (вложенные JSON-аргументы отдельно); маршрутизацию Haiku/Sonnet (классификация саппорта, языковой гейт, полировка `/broadcast`) — на ту же Qwen с малым `max_tokens` либо Qwen3.8-4B GGUF на CPU; `[[кнопки: …]]` и JSON интейка — при желании через `response_format: json_schema`. Prompt-cache работает только пока системник **байт-в-байт** одинаков (дата/время уже вынесены). `/diag` — добавить пинг `/v1/models` vLLM, `/health` ASR и Docling.
