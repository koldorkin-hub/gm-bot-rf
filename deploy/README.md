# Развёртывание РФ-сервера

Порядок действий на чистом российском сервере. Всё, что здесь есть, от выбора площадки
не зависит: и Яндекс, и Cloud.ru дают обычную виртуальную машину, а модель подключается
одной строкой в учётных данных n8n.

**Требования к машине** (research/РФ-СТЕК-03, итоговая таблица): 8+ ядер, 32 ГБ RAM,
NVMe от 200 ГБ. Из них Docling берёт 4–8 ГБ, распознавание речи 1–2 ГБ, Crawl4AI 1–2 ГБ,
остальное Postgres и n8n. Видеокарта нужна только для пути 2.

## Порядок

    # 1. Окружение
    cp .env.example .env && nano .env          # три ключа и домен, как описано в файле
    openssl rand -base64 24                    # PG_PASSWORD
    openssl rand -base64 32                    # N8N_ENCRYPTION_KEY
    openssl rand -hex 32                       # GM_FIELD_KEY (ровно 64 знака)

    # 2. Запуск. Профиль gpu НЕ включаем — на пути 1 модель берётся по API.
    docker compose pull
    docker compose up -d

    # 3. Схема данных и контур здоровья (скрипты в ../schema, проверки внутри них)
    docker compose exec -T postgres psql -U gm_app -d gm_memory -v ON_ERROR_STOP=1 \
      -f - < ../schema/... # см. ../schema/README.md, там точный порядок четырёх шагов

    # 4. Проверка фактами
    ./check.sh

    # 5. Только после зелёного check.sh — импорт workflow и учётные данные в n8n

## Что проверяет check.sh

Не «контейнер запустился», а результат:

- в базе есть таблицы, контур здоровья и справочник БЖУ;
- **белый список показателей отказывает**: попытка записать глюкозу в открытый контур падает
  (ветка отказа проверяется явно — при удачном прогоне она не исполняется и потому чаще всего сломана);
- у n8n верный часовой пояс расписаний, доступен модуль шифрования, данные успешных
  исполнений не сохраняются;
- распознавание речи принимает файл и отвечает полем `text`;
- **Docling возвращает кириллицу** — главная грабля чтения документов: русский OCR по
  умолчанию выключен, а параметр языка в запросе иногда игнорируется;
- **модель возвращает структурный вызов инструмента**, а не текст с его описанием, и число
  доезжает в аргументах. Это первое, что ломается у открытых моделей.

`./check.sh --llm-only` — быстрая проверка после смены площадки или модели.

## Что здесь намеренно НЕ описано

- **TLS и nginx.** Вебхук Telegram требует HTTPS, но обратный прокси ставится на хост, а не
  в этот compose: так его проще менять и он переживает пересборку стека. n8n слушает
  только `127.0.0.1:5678`.
- **Бэкапы.** Система бэкапов уже есть и проверена восстановлением на боевом
  (`knowledge/memory/backup-system.md`) — переносится отдельно. Ключ `GM_FIELD_KEY` кладётся
  в бэкап **отдельно от базы**: вместе они бессмысленны как защита.
- **Импорт workflow.** `ЭТАЛОН-main-workflow.json` — справочник, а не файл для импорта
  «как есть»: РФ-версия отличается моделью, голосом, документами и поиском.

## Грабли, уже стоившие времени на боевом (учтены в compose)

1. `docker compose up -d` пересоздаёт контейнер и стирает ручные патчи внутри него —
   после каждого `up -d` проверять то, что патчилось руками.
2. Останавливать n8n `docker kill`, не `docker stop`.
3. Импорт workflow даёт черновик без публикации; `staticData` при импорте не переносится.
4. Владелец таблиц Postgres должен быть тем же, под кем ходит бот, иначе `permission denied`.
5. Исполнения со статусом `running`, которые никогда не завершаются, — косметика режима
   `EXECUTIONS_DATA_SAVE_ON_SUCCESS=none`, чинить не нужно.

Подробности — `knowledge/memory/n8n-deploy-gotchas.md`.

## Статус проверки

Compose и `check.sh` разбираются без ошибок (yaml и `bash -n`), но **на живом сервере ещё
не запускались**: сервера нет, а на машине разработки запускать нельзя. Теги образов перед
первым запуском запинить по digest — в файле это отмечено. Первый прогон `./check.sh`
и будет настоящей проверкой; смотреть его вывод глазами, а не по коду возврата.
