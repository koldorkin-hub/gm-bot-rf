Собрано при построении [[backup-system]] 18.07.2026, каждая позиция реально ломала работу.

**1. Копирование `database.sqlite` даёт устаревший снимок.** n8n работает в режиме WAL, и свежие изменения лежат в `database.sqlite-wal` (на момент проверки 4.2 МБ). Обычный `docker cp` дал 1 workflow вместо 2 — то есть бэкап выглядит целым, восстанавливается без ошибок, а половины работы в нём нет. Правильный способ — `VACUUM INTO '/путь/snapshot'` через модуль `sqlite3` внутри контейнера: делает консистентный снимок живой базы без остановки n8n. В `backup.sh` стоит защита: если в снимке ноль workflow или ноль credentials, скрипт падает и шлёт уведомление, а не кладёт пустышку.

**2. `set -o pipefail` ломает проверку через gpg.** `gpg --list-packets` на файле, зашифрованном чужим публичным ключом, возвращает код 2 («No secret key»), хотя файл корректен. При pipefail код всего конвейера берётся от gpg, а не от grep, поэтому `gpg ... | grep -q ...` всегда считался неудачей. Вывод надо сначала складывать в переменную с `|| true`, и только потом проверять.

**3. У образа `n8nio/n8n` entrypoint подставляет `n8n` перед аргументами.** Поэтому `docker run ... n8nio/n8n sh -c "..."` даёт `Error: Command "sh" not found`, а `... n8n list:workflow` — `Error: Command "n8n" not found`. Для шелла нужен `--entrypoint /bin/sh`, для CLI передавать только подкоманду (`list:workflow`).

**4. PowerShell 5.1 читает .ps1 без BOM как CP1251.** Кириллица декодируется в мусор, и байт `0x94` из UTF-8-последовательности тире превращается в «умную» кавычку, которую PowerShell принимает за открывающую кавычку строки — файл разъезжается с жалобой на незакрытые скобки. Скрипты с кириллицей сохранять в UTF-8 **с BOM**. Отдельно: обратный апостроф для переноса строки ломается о CRLF (экранирует возврат каретки), поэтому переносов лучше избегать.

**5. `docker cp` кладёт файл владельцем root**, а процессы в контейнере n8n работают под `node` — импорт падает с `EACCES`. После копирования нужен `docker exec -u root <контейнер> chown node:node <файл>`. Та же грабля всплывала при ротации ключа, см. [[n8n-encryption-key-rotation]].

**6. Забор бэкапов через `scp` в планировщике Windows виснет на крупных файлах.** Поймано 23.07.2026: `pull-backup.ps1` (задача «AI Trainer — забор бэкапов», 12:00) вызывал `& scp.exe ... 2>&1` и молча вставал с 21.07 — ровно когда бандлы выросли с 3–4 МБ до 20+ МБ (в снимок sqlite попала история исполнений research). Диагноз: задача берёт СИСТЕМНЫЙ OpenSSH `C:\Windows\System32\OpenSSH\scp.exe` (9.5p2, SFTP-режим), а в windowless-сессии планировщика чтение его вывода конвейером PowerShell дедлочится/обрывается — на мелких файлах вывода мало и проскакивало, на 20+ МБ висло до убийства по 30-мин лимиту (`0xC000013A`). Провал был ТИХИЙ: сервер о pull не знает и не тревожит, а сам скрипт не дописывал даже строку ошибки в лог — виден только `=== старт ===` без продолжения. Фикс: (а) `-q` — гасит индикатор прогресса; (б) главное — запускать scp через `Start-Process -RedirectStandardOutput/Error` в файлы, а не через конвейер PS (полностью отвязывает от хоста); (в) после копирования сверять размер каждого локального бандла с серверным (`ssh ... stat -c '%s %n'`), иначе оборванный частичный файл выглядит целым и не восстановится. Общее правило снова подтвердилось: доходящий бэкап ≠ доходящий до off-site; проверять факт (размер/дешифр), а не «задача отработала».

**★ 6-bis. Забор снова встал (09.08.2026) — три наслоившихся причины, ПОЛНАЯ разгадка.** Свежайший локально был 30.07 при живом сервере (бандлы 08-09 делались штатно). Разобрано по слоям:
- **(а) Бандлы распухли до 40–124 МБ** (история исполнений n8n в снимке sqlite + research-прогоны). Скрипт качал `*.gpg` ВСЕ разом (~490 МБ) → рвалось. Фикс: скрипт переписан на **инкрементальный** (список `stat` с сервера → качаем ТОЛЬКО недостающие/битые по размеру, по одному файлу, во временный `.part` + атомарный `Move-Item` — частичные заходы накапливаются, обрыв не оставляет «псевдоцелый» файл). + серверный `backup.sh`: `vac.js` после `VACUUM INTO` **удаляет все таблицы `execution%` из снимка** и `VACUUM`; в tar тома добавлены `--exclude='n8nEventLog*' --exclude='crash.journal'`. Бандл 41→**18 МБ** (WF/CRED целы). Бэкап `backup.sh.bak-*`.
- **(б) OpenSSH в планировщике = console-паранойя.** ПЕРВОПРИЧИНА `0xC000013A`: конвейер `& ssh/scp ... 2>&1` (чтение вывода PS-хостом БЕЗ консоли) рушит процесс МГНОВЕННО (в pull-console.log виден литеральный `^C`). А `-WindowStyle Hidden` + `-RedirectStandardOutput` из windowless-сессии — падает ещё раньше. Оба ssh И scp — ТОЛЬКО через `Start-Process -NoNewWindow` + вывод в ФАЙЛ.
- **(в) Окно терминала → владелец его закрывал → CTRL+C → смерть.** Дать консоль через видимое окно нельзя — всплывающее окно владелец закрывал, убивая процесс. **РЕШЕНИЕ: скрытый VBS-лаунчер** `_backups/launch.vbs` = `WScript.Shell.Run "cmd /c powershell -File pull-backup.ps1 > pull-console.log 2>&1", 0, True` (intWindowStyle **0** = окна нет, но КОНСОЛЬ есть → OpenSSH доволен, закрывать нечего). Действие задачи → `wscript.exe "launch.vbs"`. Проверено: `Result=0x0`, окно не появляется.
- **Расписание** (по просьбе владельца, комп часто выключен): попытки **каждые 3 ч** (daily 09:00 + Repetition PT3H×PT15H) + `StartWhenAvailable` + `RestartCount 2/PT10M` + лимит PT2H. Итог: OpenSSH scp в Task Scheduler надёжен ТОЛЬКО как «скрытый VBS → cmd(консоль) → powershell → Start-Process(-NoNewWindow)+redirect-в-файл». И: `.ps1` после правок Edit/Write — ПЕРЕСОХРАНЯТЬ в UTF-8 BOM (иначе кириллица→мусор→парс-ошибки, грабля 4).

**★ 7. Забор «успешен», лог не растёт — зомби `ssh.exe` держит хэндл лога (25.08–04.09.2026).** Заход 25.08 00:00 упал на `ssh` («banner exchange… Connection timed out»), PowerShell завершился, а сам `ssh.exe` остался жить 10 дней. Он унаследовал дескриптор `pull-console.log`, куда `launch.vbs` перенаправляет вывод (`cmd /c powershell ... > pull-console.log`). Каждый следующий запуск задачи умирал на перенаправлении ещё до старта PowerShell: планировщик — `Result=0`, `pull.log` — ни строки, тревог — ноль (скрипт-то не запускался). Симптом-маркер: `Start-ScheduledTask` «отрабатывает», а `pull-console.log` не меняется; прямой запуск даёт «The process cannot access the file because it is being used by another process». Диагностика: `Get-CimInstance Win32_Process | ? { $_.Name -in 'ssh.exe','scp.exe' }` — смотреть на дату создания. Лечение: `Stop-Process -Id <pid> -Force`. Главный вывод: **самопроверка внутри скрипта не ловит случай «скрипт не запускается»** — поэтому свежесть бандлов теперь проверяет независимый `healthcheck.ps1` (каждые 5 мин: возраст свежайшего `*.gpg` > 30 ч три раза подряд → тревога с подсказкой, висит ли процесс забора; повтор раз в сутки; «снова свежие» отдельно; ветки `-TestBackup`/`-TestRecovery`). См. [[bot-self-diagnostics]].

**★ 7-bis. ПЕРВОПРИЧИНА зомби найдена и закрыта (07.09.2026, повтор случая 7).** Через сутки после постройки сторожа он сработал: бандл 30.3 ч, `ssh.exe` висел 13 часов с 00:00, вся цепочка `cmd → powershell → ssh` жива, задача рапортует `result=0`. **Первопричина: `-o ConnectTimeout=30` защищает ТОЛЬКО установку соединения.** Если TCP уже установлен и канал молча умер, ssh ждёт вечно — таймаута на чтение у него нет по умолчанию. Отсюда и живучесть зомби. Поставлено три уровня:
1. **Keepalive в самом ssh/scp:** `-o ServerAliveInterval=15 -o ServerAliveCountMax=4` — ssh сам умирает после ~60 с тишины на установленном соединении. Это и есть лечение причины.
2. **Жёсткий таймаут в скрипте:** `Start-Process -Wait` ждёт бесконечно, поэтому заменён на `-PassThru` + `WaitForExit(мс)` + `Kill()`. Лимиты: 120 с на список бандлов, 900 с на один бандл (40 МБ).
3. **Уборка перед стартом:** `_backups/kill-stale-pull.ps1` снимает процессы прошлого запуска старше 60 минут; вызывается из `launch.vbs` ОТДЕЛЬНЫМ `sh.Run` ДО основного, потому что ломается именно перенаправление вывода (`> pull-console.log`), и внутри самого забора уборка бы уже не запустилась. Бьёт узко: ssh/scp — только с нашим ключом или адресом сервера в командной строке (посторонние сессии не трогает), powershell/cmd — только по полному пути `pull-backup.ps1`; себя и цепочку родителей исключает; есть `-WhatIfOnly` для сухого прогона.

**Две грабли PowerShell, пойманные юнит-тестом при этой правке (обе молчаливые):**
- **`Write-Log` пишет и в поток вывода** (`Write-Output $line`), поэтому вызов логирования внутри функции подмешивается в её возвращаемое значение: `return $null` после `Write-Log` отдаёт массив `[строка, $null]`, и проверка `if ($null -eq $code)` уходит не в ту ветку. Лечится `Write-Log ... | Out-Null` внутри функций, которые что-то возвращают.
- **Без `-Wait` объект `Start-Process -PassThru` теряет `.ExitCode`** — приходит пустота вместо кода возврата. Лечится обращением к `$p.Handle` сразу после запуска (кэширует дескриптор). Поймано тестом «процесс завершился с кодом 7 → получили пустую строку».

Мораль на будущее: **любую правку скрипта проверять синтетикой на все три исхода** (завис / успех / ошибка), а не только на «работает как раньше». Обе грабли выше прошли бы боевой прогон незамеченными, потому что при успешном заборе ветки ошибок не исполняются. Откаты: `pull-backup.ps1.bak-20260907`, `launch.vbs.bak-20260907`.
