Структурированное хранилище данных о клиенте (профиль, измерения, тренировки, еда, коллекции, артефакты, производная память) — решает «бот помнит клиента, не перечитывая год переписки». Всё в существующем Postgres `n8n_memory`, схема `public`, рядом с `clients`/`n8n_chat_histories`. Полный дизайн с DDL — файл `ПАМЯТЬ-схема-v1.md` в корне проекта; исходники схемы — `schema/memory-wave1.sql` (+ `-rollback.sql`), они же на боевом в `/root/memory-block/`.

**Организующий принцип — по ФОРМЕ хранения, не по теме.** 6 хранилищ: (1) `client_profile` — одна строка/клиент, читается каждое сообщение; (2) `measurement` — ОДНА универсальная таблица «дата→метрика→число» на всё (вес, обхваты, анализы, сон, любая произвольная метрика без смены схемы), читается только агрегатами; (3) журналы `workout_session`+`workout_entry` (мультиформат: `kind` разводит силовые построчно / кардио своими полями) и `food_log`; (4) коллекции `allergen`/`food_preference`/`medication`/`condition`/`injury` + `exclusion` (главная для безопасности, проверяется кодом); (5) артефакты `recipe`+`recipe_ingredient`/`research_report`/`plan`; (6) производная память `client_summary`/`extraction_state`/`chat_history_archive`. Справочники: `activity_library` (теги нагрузки `load_tags text[]` — основа проверки исключений на все виды спорта), `freshness_policy` (пороги свежести). Волна 2 (не создано): `personal_record`, `coaching_note`, `food_reference`.

**Ключ везде составной — ДВЕ колонки `bot_id text` + `user_id bigint`** (не единая строка), `bot_id REFERENCES clients(bot_id)`. Мост к существующей памяти: `session_id = bot_id||':'||user_id` (в `n8n_chat_histories` ключ — именно эта строка). Утверждённые решения владельца 23.07.2026: дисциплины — jsonb-список в профиле; силовой журнал — строка на подход; PDF отчётов — `bytea` в Postgres. Все таблицы владелец `n8n_user` (иначе бот получит permission denied — см. [[n8n-postgres-gotchas]]).

**Механизм извлечения (Хранилище 6):** ночной workflow (планируется `MemoryExtract0001`), Sonnet + structured output читает новый срез переписки по водяному знаку `extraction_state.last_message_id`, раскладывает: числа → `measurement`, медфакты → коллекции с `confirmed=false` (бот подтвердит), смысл → `client_summary`; старьё архивируется в `chat_history_archive`. Порог архивации ОБЯЗАН быть ≥ окна агента (узел `memoryPostgresChat` читает последние N) — проверять живьём.

- **Новые durable-поля `client_profile`** (миграции): `custom_instructions` (персональные настройки бота, свободной фразой), `active_plan` (общий/долгосрочный план — спорт+питание+добавки+фарма+любые договорённости), `plan_month`, `plan_week`. Все — в whitelist+upsert `ProfileTool00001` (`transform-profiletool-*`), инжектятся в Build Profile Context, описаны в save_profile. **Три горизонта плана НЕЗАВИСИМЫ** — сохранение одного не трогает другие; поля профиля ПЕРЕЗАПИСЫВАЕМЫ (можно заменить план на новый — в отличие от журналов, где строки не удалить). Правила — в systemMessage (`transform-main-plans-multi.js`, `-custom-instructions.js`).
- **systemMessage «ПАМЯТЬ И ВЕДЕНИЕ КЛИЕНТА»**: НЕ существует «суточных сессий»; еду/тренировки логировать сразу; когда спрашивают «что записано / найди X» — ВСЕГДА звать get_progress, НИКОГДА не отвечать «пусто/не помню» без проверки БД; согласованный план сохранять в поля плана.
- **Часовой пояс клиента** (`transform-main-timezone.js`): Build Profile Context детерминированно считает дату+время+день недели в `prof.timezone` (default Europe/Moscow) через `toLocaleString('sv-SE',{timeZone})` и кладёт строку «СЕЙЧАС У КЛИЕНТА …» ПЕРВОЙ; systemMessage ТЕКУЩАЯ ДАТА отсылает к ней. Серверные часы проверены — верны, NTP-синхронны.
- **Дробление тренировки** (`transform-logworkout-session-reuse.js`): узел «Сессия» ВСЕГДА делал INSERT → одна тренировка из многих сообщений дробилась на N сессий. Стало НАЙТИ-ИЛИ-СОЗДАТЬ сессию за (bot,user,performed_on) — строки дополняют одну.
- **Анти-дубль еды**: правило в systemMessage — одно блюдо/подход логируется ОДИН раз; для итога дня ЧИТАТЬ get_progress, не пересоздавать записи.

**★ ДНЕВНИК ПО ДНЯМ + ДЕНЬ ПРОГРАММЫ (чат 8, 12.08.2026).** Продолжение фикса непрерывности: владелец жаловался «вся еда/тренировки слиты в одно, день программы не знает». **Корень: хранилище было верным (всё по дням), сломан слой чтения** — `get_progress` отдавал только агрегаты за период без дат/состава; конкретный день запросить было нельзя.
