Команда `/research <вопрос>` запускает доказательный разбор: PubMed как ядро, веб-поиск как вспомогательный контекст, синтез на Opus, краткое саммари в чат + полный PDF-отчёт файлом. Построено и проверено живьём 21.07.2026.

**Устройство.** Перехват — правило `research` ПЕРВЫМ в `Switch` (выходы стали `[0]=research, [1]=voice, [2]=text`; `allMatchingOutputs=false`, поэтому первое совпадение выигрывает). Сам цикл — подчинённый workflow `ResearchTool0001`, вызываемый узлом `executeWorkflow`.

**Цикл** (`Инициализация` → план → `Сбор доказательств` ⇄ `аудит пробелов` → синтез → PDF):
- состояние несётся в `$json` по цепочке; ссылки — только на узлы, выполняющиеся ОДИН раз (`Инициализация`, `Разобрать план`), плюс на собственный предыдущий прогон;
- номер витка — `$runIndex`, не самодельный счётчик;
- условие продолжения считается в Code (`should_continue`), IF остаётся тривиальным;
- PubMed зовётся из Code через `this.helpers.httpRequest` (для NCBI-ключа — `httpRequestWithAuthentication` с фолбэком на без ключа), XML разбирается регулярками: внешних модулей в песочнице нет.
- Аудитор на КАЖДОМ витке проверяет односторонность набора и добирает противоречия/риски — это защита в отборе источников, а не только в промпте синтеза. Живой прогон: аудитор сам назвал перекос «в сторону обзоров одной исследовательской группы» и следующим витком пошёл искать нулевые результаты и нефротоксичность.

**Лимит.** Списание при ЗАПУСКЕ атомарным upsert (`WHERE used < research_daily_limit ... RETURNING`); ноль строк = лимит исчерпан. На узле обязателен `alwaysOutputData: true`, иначе ветка молча обрывается и клиент не получает ничего. Возврат — ОДИН SQL через леджер `research_attempts` (PK = `execution_id`): `UPDATE ... WHERE refunded = false` структурно исключает двойной возврат. Возврат живёт ровно в одном месте — ветки ошибок узлов доставки и цикла; в глобальный Error Workflow его добавлять НЕЛЬЗЯ (второй путь = двойной возврат).

**Параметры** — таблица `research_config` (одна строка): `max_sources` 20, `max_iterations` 4, `max_web_searches` 6, `model_synthesis` Opus (синтез и чтение источников), `model_helper` Sonnet (планировщик и аудитор), `legal_prompt`. Меняются SQL-ом без передеплоя; при недоступности БД — безопасные дефолты в коде.

**Режим владельца** — колонка `clients.owner_mode`, **DEFAULT false**: новый клиент фокус-группы автоматически получает полные ограничения, включить режим можно только явным UPDATE по конкретному `bot_id`. Что меняется при `owner_mode = true`: лимит не списывается (SQL возвращает строку-пропуск `unlimited=true`, строки в `research_usage` не создаются), в синтезе действует `research_config.owner_prompt` вместо `legal_prompt`, из PDF убирается блок дисклеймера, добавляется раздел «Практические выводы» с прямыми указаниями читателю. Качество разбора не трогается: противоречия, ограничения, риски и ссылки остаются в обоих режимах — это не ограничение, а польза.
Важно: снять юр.рамку мало. Без раздела практических выводов структура «научный обзор» сама по себе не даёт применимых заключений, и разница между режимами остаётся формальной — замер показал 0 прямых указаний в обоих режимах, пока раздел не добавили. Возврат лимита учитывает `research_attempts.charged`: у владельца списания не было, значит попытка помечается `failed`, но `refunded` остаётся false и счётчик не трогается.

**Юр.рамка** живёт в `research_config.legal_prompt` — ГЛОБАЛЬНО, а не в `clients.system_prompt`, чтобы её нельзя было отключить на уровне клиента (клиентский режим). Проверено на доставленном PDF: ноль персональных рекомендаций, 60 ссылок [N], 20 PMID, в ограничениях честно указано финансирование производителем как конфликт интересов. Если PubMed недоступен и собрано НОЛЬ источников — синтез намеренно роняется, отчёт «по памяти модели» не выдаётся.

**PDF.** HTML → Gotenberg → `Extract from File` (операция pdf, `keepSource: both`) → проверка текста. Дисклеймер рамкой в САМОМ начале, до резюме; для фарма-тем усиленная формулировка про «дозировки — описание экспериментов, а не назначение».

**Задел на будущее (п.11):** узел `Собрать отчёт` держит в одном месте `summary_for_chat`, `report_text`, `report` и `sources`; таблица `research_attempts` — готовая точка для колонок `report_text`/`pdf`. Добавить хранение = повесить Postgres-узел после `Собрать отчёт`, поток переделывать не придётся.

**Тайминг:** полный разбор 7–11 мин (веб-контекст — основной вклад). `executionTimeout` подчинённого 1500 с внутри `EXECUTIONS_TIMEOUT=1800`.

**Грабля JSON-парсинга (01.08.2026): `claude-opus-4-8` кладёт в строковые значения JSON СЫРЫЕ управляющие символы** (непроэкранированные переносы строк внутри `summary` и т.п.) → `JSON.parse` падает «Bad control character in string literal», ломая КАЖДЫЙ разбор на «Собрать отчёт» (симптом «Синтез не вернул структурированный отчёт»; цикл при этом отрабатывает полностью, включая web_search и корректный отказ по запрещёнке). Причём `content[0]` теперь может быть пустым `thinking`-блоком (в теле синтеза thinking включён) — узел уже фильтрует `type==='text'`, так что дело именно в control-символах. Починка: `parseLoose` во всех трёх парсерах (`Собрать отчёт`, `Разобрать план`, `Разобрать аудит`) при ошибке делает 2-й заход через `__sanitizeCtrl` — экранирует управляющие символы ТОЛЬКО внутри строковых литералов (структуру JSON не трогает). Исходник `schema/transform-research-json-sanitize.js`. Проверено на реальном упавшем ответе (8434 симв → распарсилось).
