Настроено 09.09.2026 по просьбе владельца: он часто в дороге и хочет вести разработку с телефона.

**Как это работает.** На сервере Fornex стоит Claude Code (`/usr/local/bin/claude`). Каждая беседа, которую владелец видит в приложении на телефоне, — это systemd-служба из шаблона `/etc/systemd/system/claude-rc@.service`, запускающая `claude remote-control`. Экземпляр службы шаблона = рабочий каталог (`%f`), поэтому через шаблон два экземпляра в одном каталоге не завести. **Но само ограничение мнимое:** `claude remote-control` спокойно запускается вторым процессом в том же каталоге — проверено 09.09.2026, обе службы держатся. Достаточно написать для второй беседы обычный unit-файл (не из шаблона) с тем же `WorkingDirectory`.

**Это важно для группировки в приложении:** беседы там группируются по имени каталога. Разные каталоги = разные группы в списке, и связанные беседы разъезжаются по экрану. Поэтому беседы одного проекта держим в ОДНОМ каталоге: они видят одни файлы, одну историю git и одни знания, а в приложении стоят рядом одной группой.

Имя, видимое в приложении, задаётся флагом `--name`. В шаблоне оно выводится из пути (`server:/root/...`) и в списке читается плохо, поэтому для каждой беседы кладём drop-in `/etc/systemd/system/<unit>.d/name.conf` с пустым `ExecStart=` и своим — с человеческим именем. Кириллица в имени работает.

Добавить новую беседу:
```
mkdir -p /root/projects/<путь>
UNIT=$(systemd-escape -p --template=claude-rc@.service /root/projects/<путь>)
# drop-in с --name, затем:
systemctl daemon-reload && systemctl enable --now "$UNIT"
```

**Проект GM Bot RF** (российская версия Тренера): `/root/projects/gm-bot-rf` — беседа «GM Bot RF — разработка», `/root/projects/gm-bot-rf/marketing` — «GM Bot RF — маркетинг». Один git-репозиторий, origin — голый репозиторий на том же сервере `/root/git/gm-bot-rf.git` (GitHub добавляется вторым удалённым адресом, `gh` на сервере не установлен). Модель обеих — `claude-opus-5`, задана ключом `"model"` в `.claude/settings.json` проекта: **у `claude remote-control` нет флага `--model`**.

⚠️ **Грабля 1: доверие к каталогу.** Служба падает с `Error: Workspace not trusted` и уходит в цикл перезапусков, пока каталог не отмечен доверенным. Флаг живёт в `/root/.claude.json` → `projects["<путь>"].hasTrustDialogAccepted = true`. Интерактивный диалог в systemd показать негде, поэтому проставлять прямо в файле (с резервной копией и атомарной записью — файл большой и его переписывает сам Claude).

⚠️ **Грабля 2: правила `Write(...)` в настройках НЕ РАБОТАЮТ.** Claude Code проверяет файловые операции только по правилам `Edit(...)`, и они покрывают все инструменты правки, включая Write. Правило `Write(//opt/**)` в `deny` не срабатывает вообще и лишь сыплет предупреждением при каждом запуске. Поймано фактической проверкой (`claude --print` в каталоге проекта показал предупреждения), а не чтением документации. **Проверять любые правила доступа прогоном, а не глазами.**

**Защита боевого.** Службы работают в режиме автоподтверждения (`--permission-mode auto`), поэтому единственный барьер — `deny` в настройках проекта. Запрещены `docker`, `psql`, `pg_dump/restore`, `ufw`, `iptables`, `nft`, `nginx`, `certbot` и правка `/opt`, `/etc`, `/var`, `/root/memory-block`, `/root/projects/eol-lawyer`. Настройки прописаны **в каждом каталоге отдельно** — наследование из родительского проекта не проверялось, полагаться на него на боевой машине нельзя.

**Известный пробел не в нашем проекте:** в глобальном `/root/.claude/settings.json` запрет `Write(//root/projects/eol-lawyer/.env)` по той же причине не действует — файл с секретами юриста от правки не защищён. Владельцу сообщено, менять чужой проект без спроса не стал.

**Про лимиты (частый вопрос владельца).** Контекст беседы при заполнении сжимается сам, беседа продолжается — создавать новые чаты, как в приложении, не нужно; служба вдобавок перезапускается автоматически. А вот лимит использования аккаунта общий на все сессии сразу (серверные беседы, ноутбук, Гермес) — новые чаты его не обходят.

**★ Грабля: выгрузка workflow n8n несёт живые токены — в `staticData` (09.09.2026).** Расхожее мнение «n8n держит секреты в отдельной таблице credentials, в выгрузке их нет» верно только про сами credentials. В `export:workflow` целиком попадает `staticData`, а у Тренера там лежит **кэш токенов всех четырёх ботов** (`staticData.global.tokens.*`) — сделанный намеренно ради отказоустойчивости при падении Postgres, см. [[n8n-resilience]]. То есть это не забытый секрет, а работающая часть конструкции, но выгрузку она делает секретосодержащей.

Поймано при подготовке эталонной выгрузки для репозитория, который уходит на GitHub — откуда секрет из истории не вычистить. **Правило: выгрузка workflow перед попаданием в репозиторий проверяется регулярками на секреты, и в первую очередь смотреть `staticData`, а не узлы** (поиск по узлам ничего не даёт и создаёт ложное чувство безопасности — проверено, именно так и вышло). Найденное заменять метками с сохранением структуры и проверять результат повторным поиском. Побочно: `staticData` импорт workflow не переносит, поэтому вычищенный файл всё равно не предназначен для импорта.

**★ Грабля: `--continue` у remote-control ломает беседу после паузы (09.09.2026).** Чтобы вернуть уже начатую переписку после перезапуска службы, нужен флаг `--continue` — он переподключает к последней сессии этого каталога. Но у него два побочных свойства: (1) переводит службу в режим одной сессии («Single session · exits when complete»), то есть процесс выходит по завершении сессии, и (2) **падает с ошибкой, если для каталога ничего не записано за последние ~4 часа**. Вместе это значит: после долгой паузы служба уходит в цикл перезапусков и беседа пропадает из приложения.

Решение — обёртка `/usr/local/bin/claude-rc-continue "<имя>"`: пробует `--continue`, при ненулевом коде возврата поднимает обычную беседу, чтобы чат был доступен в любом случае. Плюс `RestartSec=3` вместо 10, чтобы разрыв был короче.

**★ История беседы привязана к каталогу.** Сессии лежат в `~/.claude/projects/<путь-с-заменой-/-на-->/*.jsonl`. Перенести беседу в другой каталог штатно нельзя — `--continue` ищет запись именно для своего каталога. Поэтому **нельзя менять рабочий каталог беседы, в которой уже велась работа**: поймано 09.09.2026 при попытке свести две беседы проекта в одну папку ради группировки в приложении — у владельца пропала маркетинговая переписка на 83 сообщения. Восстановлено возвратом службы в исходный каталог. Перед любой такой правкой: `cp` файлов сессии в `/root/backups/` и сверка реплик владельца до и после.

**Про группировку в приложении:** беседы группируются по имени каталога, и это чисто косметика. Если подпапка лежит внутри репозитория проекта, беседа из неё всё равно видит все файлы проекта на уровень выше — содержательной изоляции нет. Ради красоты списка историю не двигать.
