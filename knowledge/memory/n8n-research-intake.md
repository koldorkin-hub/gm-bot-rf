**research-B (построен 01.08.2026)** — стейт-машина интейка перед циклом [[n8n-research-mode]]. Решает проблему: раньше `/research` без темы спрашивал тему, но БЕЗ состояния — ответ клиента уходил в обычного агента, команда терялась (фикс A `Research: тема?` только спрашивал). Теперь состояние держится в Postgres.

**★ ОБНОВЛЕНИЕ 05.08.2026 (чат 6) — ОДНВОПРОСНЫЙ интейк (тема+цель ОДНИМ сообщением).** Было два вопроса (тема → цель), стало один. Изменения (`schema/transform-main-research-oneshot.js`): (1) пустой `/research` → `ждём тему` ставит **`awaiting_goal`** (topic=NULL, БЫЛО awaiting_topic), `спроси тему` — ОДИН комбинированный вопрос (тема+цель); ответ → `маршрут`[awaiting_goal] → `взять цель` (query=text) → run. (2) инлайн `/research <текст>` → `есть тема?`[да] → `сохранить тему` (создаёт строку research_state, нужна для UPDATE в `пометить running`) → **перемычка на `взять цель`** (БЫЛО → `вопрос цели`) → run НАПРЯМУЮ. `взять цель` теперь **inline-aware**: `let start=null; try{start=$('Research: старт').first().json;}catch(e){}` — если пришли инлайном (старт исполнялся, hasTopic) query = весь текст после /research; иначе прежняя склейка `[topic,text].join(' — ')` (topic из `интейк?` через try/catch — в инлайн-пути `интейк?` не исполнялся). `Research: вопрос цели` осиротел (безвреден). `awaiting_topic` больше НЕ ставится (легаси-стадия; `взять тему`/`маршрут`[out0] уцелели, безвредны). Фарма-пивот/лимит-refund/busy-гейт НЕ тронуты. Проверено вживую (owner, на разных ботах параллельно): пустой→1 вопрос→ответ→«Ушёл искать»; инлайн→сразу «Ушёл искать»; query захвачен верно.

**Таблица** `research_state(bot_id, user_id, stage, topic, chat_id, started_at)` PK(bot_id,user_id). stage: `awaiting_topic` / `awaiting_goal` / `running`.

**Поток (узлы в main):**
- **(A) ранний гейт занятости:** `Пущен?`[true] → `Research: занят?` (SELECT EXISTS running) → `Research: занят!` → [running] `Research: подожди` (ЛЮБОЕ сообщение блокируется, агента не дёргаем) / [нет] `Load Profile` (обычный путь). Гейт ДО Switch → ловит текст/голос/фото за один PG-запрос, без транскрипции.
- **(B) `/research`:** Switch out0 → `Research: старт` (парс inline-темы после /research) → `есть тема?` → [да] `сохранить тему` (awaiting_goal, `RETURNING topic`) + `спросить цель` / [нет] `ждём тему` (awaiting_topic) + `спроси тему`.
- **(C) текст+голос сведены:** Switch out5 (текст) И `Edit Fields` (голос, после транскрипта) → **общий** `Research: интейк?` (SELECT stage/topic, COALESCE→'none') → `Research: маршрут` (Switch по stage): `awaiting_topic`→`взять тему`→сохранить+спросить цель; `awaiting_goal`→`взять цель` (склейка `тема — цель`)→`списать лимит`→[ok] `пометить running`+`ушёл искать`→существующий цикл; `none`→`обычный?`→[голос]AI Agent/[текст]Текст: копит?.
- **(D) снятие:** терминалы (`отметить успех`/`вернуть попытку`/`к врачу`/`лимит исчерпан`/`не смог запустить`) → `Research: снять running` (DELETE строки).

**Грабли/решения:**
- **Источник текста в Code-узлах** (`взять тему`/`взять цель`): голос → `$('Edit Fields').first().json.message.text` (транскрипт), текст → `$('Normalize').message.text`; выбор по `$('Normalize').message.voice !== undefined`. Тернарник в JS не вычисляет ветку голоса для текстового исполнения → `$('Edit Fields')` (неисполненный узел) не дёргается. user_id/chat всегда из `$('Normalize')` (Edit Fields несёт только message.text).
- **Цикл** теперь берёт query из `$('Research: взять цель').first().json.query`, НЕ из /research-текста (`Research: цикл`.workflowInputs.value.query переписан). Единственный путь к циклу — через awaiting_goal, поэтому ссылка валидна.
- **Уточнение цели — ДЕТЕРМИНИРОВАННОЕ** (правка b2 01.08.2026 после живого теста): `сохранить тему` → `Research: вопрос цели` (фикс. sendMessage «тема: X; для чего тебе разбор? напиши цель одним сообщением; профиль уже есть»), БЕЗ основного агента. Почему сменили: раньше уточнял главный агент (`Research: спросить цель`→AI Agent) — и он **уходил в онбординг** (спрашивал возраст/рост/вес, хотя профиль есть) и в обычный диалог, теряя нить; клиент рисковал получить текст вместо PDF. `Research: спросить цель` (Set) осиротел. Профиль в разбор всё равно попадает (Load Profile + цикл), онбординг в интейке не нужен.
- **Агент перенаправляет на /research** (b2): в systemMessage блок «=== РАЗБОРЫ И ИССЛЕДОВАНИЯ ===» — основной агент САМ доказательные разборы/исследования/«расклады» текстом НЕ пишет; на такую просьбу отвечает «это /research, запусти команду и назови тему». Иначе агент подменял PDF текстовым «планом», клиент разницы не видел. Обычные тренерские вопросы отвечает как обычно.
- **Фарма в /research → удержание интейка** (b2): фарма ловится ПОСЛЕ цикла (флаг `refused_pharma` из ResearchTool/Фарма-гейт → `Research: фарма-блок?` → `возврат фарма` рефанд лимита → `Research: к врачу`). Раньше `к врачу`→`снять running` (состояние очищалось, продолжение «остальное дашь» падало в обычный чат). Теперь `к врачу`→`Research: легальный пивот` + текст предлагает написать легальную тему → интейк жив, следующая тема идёт в разбор, а не в чат. **b3 (01.08.2026):** пивот ставит `awaiting_goal` (НЕ awaiting_topic) с пустой темой — чтобы НЕ спрашивать цель повторно (клиент уже назвал её до отказа; повтор раздражал). Следующий ответ клиента → `взять цель` → запуск сразу. `взять цель` склейка чинена: `query = [topic, text].filter(Boolean).join(' — ')` — при пустой теме query = сам текст (без ведущего тире). Так пивот-тема уходит в разбор одним сообщением. **b4:** текст пивота просит клиента дать легальную **тему И цель ОДНИМ сообщением** — чтобы цель попадала в запрос (не терялась). Нельзя авто-переиспользовать первую цель клиента: она часто содержит фарму (в тесте цель была «скинуть 10 кг… тестостерон/ААС»), подстановка её в легальный запрос → фарма-гейт снова отказывает → бесконечная петля пивота; детерминированно вычистить фарму из цели нельзя. Поэтому на пивоте клиент формулирует легальную тему+цель заново (одно сообщение) = цель используется, повтора-вопроса нет, петли нет. В ОБЫЧНОМ (не пивот) потоке цель захватывается штатно (topic→цель?→goal→query «topic — goal»).
- **Общий `сохранить тему`** читает `$json.topic` (от `взять тему` ИЛИ от `есть тема?`-пути) → одна нода на оба источника; `RETURNING topic` тащит тему дальше в `спросить цель` (иначе PG-выход затирает $json).
- Фикс A `Research: тема?` осиротел (Switch out0 больше не смотрит) — безвреден.

**Самоизлечение зависшего состояния (01.08.2026).** `running` снимается через терминалы (успех/возврат/…→`снять running`). НО если процесс main убит (мой рестарт n8n / краш) ДО того, как отработал `снять running` — строка `running` осиротеет, и клиент навсегда заперт на «подожди». Защита: **протухание по времени** — `Research: занят?` считает `running` активным только `started_at > now() - interval '20 minutes'` (полный разбор ≤11–25 мин; на таймауте цикла running снимается штатно через error-путь, орфан бывает лишь при убийстве процесса). Брошенный `awaiting_topic/awaiting_goal` протухает через 40 мин в `Research: интейк?`. Клиент разблокируется САМ в момент следующего сообщения, без ручного вмешательства. При деплое (рестарт n8n) орфан всё равно возможен, но живёт максимум 20 мин. Исходник `schema/transform-main-research-stale.js`. Ручной сброс: `DELETE FROM research_state WHERE bot_id=... AND user_id=...`.

**Проактивное «бот снова готов» (01.08.2026).** Протухание разблокирует молча — клиент, ушедший после серии «жди», не узнаёт, что бот вернулся. Два слоя уведомления: (1) **штатный сбой** (парсер/веб/таймаут, процесс жив) — ветка ошибки `Research: цикл`→`вернуть попытку`→`Research: сбой` пишет клиенту «🟢 снова в строю, попытка не засчитана, пришли ещё раз» + `снять running`. (2) **процесс убит** (мой рестарт/краш — ни один узел не отработал) — **свип-сторож в `PhotoBatchSweep1`** (расписание 30с, веер: `Найти зависшие`[фото] + `Research: сироты`): `WITH dead AS (DELETE FROM research_state WHERE stage='running' AND started_at < now()-interval '25 minutes' RETURNING …) SELECT … JOIN clients` — атомарно снимает орфан (25 мин = таймаут цикла, точно мёртв) и `Research: буди клиента` (httpRequest sendMessage по chat_id+bot_token из строки) шлёт «🟢 снова в строю, пришли ещё раз». `DELETE…RETURNING` = будим ровно раз. Исходник `schema/transform-sweep-research-orphan.js`. Проверено: мёртвый (26 мин) возвращается+удаляется, живой (5 мин) не тронут. Порог свипа (25 мин) > занят?-свежести (20 мин): клиент может вернуться раньше сам, сторож добивает брошенные.
