# Блок ПАМЯТЬ И ДАННЫЕ — схема на утверждение (Фаза 1)

Черновик от 23.07.2026. **Ничего в проде не менялось** — это проект схемы.
База `n8n_memory`, все таблицы владелец `n8n_user`, схема `public`.

---

## 0. Сквозные соглашения

**Составной ключ клиента.** Везде две колонки: `bot_id text` + `user_id bigint`.
- `bot_id` → `REFERENCES clients(bot_id)` (изоляция арендатора + FK).
- `user_id` = Telegram `message.from.id` (bigint). В существующей памяти это второй сегмент
  `session_id` (`'gymak:255171226'`). Мост в обе стороны: `session_id = bot_id || ':' || user_id`.
- **Почему две колонки, а не одна строка session_id:** чистые запросы и агрегаты (`WHERE bot_id=? AND user_id=?`),
  честный FK на `clients`, индексы. Строку `session_id` собираем на лету только когда надо сходить в
  `n8n_chat_histories`. Это решение — на ваше подтверждение (п. РЕШЕНИЯ).

**Общие поля.** Где уместно: `source text` (`client` — сам сказал / `extracted` — бот извлёк / `device`),
`confirmed boolean` (подтверждено человеком — для медзначимых), `created_at/recorded_at timestamptz DEFAULT now()`.

**Ключи.** Многострочные таблицы: `id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`.
Одна-строка-на-клиента (профиль, выжимка, состояние извлечения): PK = `(bot_id, user_id)`.

**Даты.** День замера/события — `date`; момент записи — `timestamptz`.

**Изоляция и GDPR-seam.** Единый ключ `(bot_id, user_id)` во ВСЕХ персональных таблицах — это и есть
дешёвый seam: экспорт/удаление клиента = проход по таблицам с этим ключом. Функцию `fn_purge_client`
/`fn_export_client` добавим позже без перекройки (место заложено единообразием ключа).

**Пометка чувствительности.** Медтаблицы (профиль, аллергены, состояния, травмы, препараты, «анализные»
измерения) несут `sensitive boolean DEFAULT true`. Пока флаг просто хранится — seam под будущую политику.

## ХРАНИЛИЩЕ 2 — ИЗМЕРЕНИЯ (универсальный ряд, ОДНА таблица на всё «дата→число»)

```sql
CREATE TABLE measurement (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  bot_id text NOT NULL REFERENCES clients(bot_id),
  user_id bigint NOT NULL,
  measured_on date NOT NULL,
  metric text NOT NULL,        -- 'weight','waist','body_fat_pct','systolic','resting_hr',
                               -- 'sleep_hours','water_ml','mood','ldl' ... и ЛЮБАЯ произвольная
  value numeric NOT NULL,
  unit text,                   -- 'kg','cm','%','mmHg','bpm','h','ml','score'
  source text NOT NULL DEFAULT 'client' CHECK (source IN ('client','extracted','device')),
  sensitive boolean NOT NULL DEFAULT false,   -- true для анализов
  note text,
  recorded_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX measurement_lookup ON measurement (bot_id, user_id, metric, measured_on DESC);
```
- Любая новая метрика («веди трекинг кофе») — без изменения схемы: новое значение `metric`.
- **Читается ТОЛЬКО** запросами по датам/агрегатами (последнее, среднее за неделю, за месяц). Никогда целиком.
- Волна 1 наполняет как минимум `weight`; обхваты/жир/анализы/сон/вода — та же таблица, волна 2.

**ТАБЛИЦА ИСКЛЮЧЕНИЙ — главная для безопасности.** Всё запрещённое из любого источника; её проверяет
Code перед выдачей рекомендаций.
```sql
CREATE TABLE exclusion (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  bot_id text NOT NULL REFERENCES clients(bot_id), user_id bigint NOT NULL,
  scope text NOT NULL CHECK (scope IN ('load_tag','activity','ingredient','other')),
  value text NOT NULL,             -- 'axial' | 'back squat' | 'peanut' ...
  source_type text NOT NULL CHECK (source_type IN
        ('injury','condition','medication','client_request','research','coach')),
  source_ref bigint,               -- id записи-первоисточника (nullable)
  confirmed boolean NOT NULL DEFAULT false,   -- подтверждено человеком
  active boolean NOT NULL DEFAULT true,       -- активно ли сейчас
  since date, until date,
  note text, created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX exclusion_active ON exclusion (bot_id, user_id) WHERE active;
```
`scope='load_tag'` + `value='axial'` блокирует ВСЕ активности с этим тегом нагрузки (работает на все виды
спорта). `scope='activity'/'ingredient'` — точечно. `source_type` хранит, откуда прилетело; при закрытии
травмы её исключения гасятся (`active=false`), а не удаляются (аудит).

## СЛОЙ ПРОВЕРОК (Code-узлы, НЕ модель; перед выдачей рекомендаций)

Таблиц почти не требует — это логика поверх хранилищ. Единственная конфиг-таблица:
```sql
CREATE TABLE freshness_policy (
  metric text PRIMARY KEY,     -- 'weight','waist','body_fat_pct','labs',...
  max_age_days int NOT NULL,
  note text
);
-- сид: weight=7, waist=30, body_fat_pct=30, labs=180, resting_hr=14 ...
```
- **Проверка аллергенов:** ингредиенты рецепта (`recipe_ingredient`) против `allergen` клиента; совпадение → выдача БЛОКИРУЕТСЯ. Не доверять памяти модели.
- **Проверка исключений:** теги предлагаемых активностей (`activity_library.load_tags`) и сами активности против `exclusion` (`active=true`). Совпадение по тегу или имени → активность не рекомендуется.
- **Проверка свежести:** перед расчётом — данные не старше `freshness_policy.max_age_days`, иначе не считать, просить обновить.
- **Калькуляторы (Code):** БЖУ, TDEE/норма калорий, дефицит/профицит, % от 1ПМ, БЖУ рецепта. Считает КОД. В промпте — прямой запрет модели считать самой; тест «посчитай сам без скриптов» должен НЕ проходить.

## ИЗВЛЕЧЕНИЕ (наполнение Хранилища 6) — механизм

- **Носитель:** отдельный workflow `MemoryExtract0001`, `ScheduleTrigger` ночью ~04:10 МСК (после бэкапа 03:40, вне часов research). Плюс лёгкий порог по объёму (если клиент за день дал > N новых сообщений — извлечь раньше); волна 1 — только ночь, порог добавляется тривиально.
- **Отбор:** для каждого активного клиента с новыми сообщениями берём срез `n8n_chat_histories WHERE session_id = bot_id||':'||user_id AND id > extraction_state.last_message_id ORDER BY id`.
- **Модель:** `claude-sonnet-4-6`, `effort: medium`, структурированный вывод (tool-схема). Opus здесь избыточен и дорог; извлечение — рутинная разметка. Схема ответа: `{ measurements:[{metric,value,unit,measured_on}], collections:{allergens:[],preferences:[],conditions:[],injuries:[],medications:[]}, summary_delta:text, coaching_notes:[] }`.
- **Маршрутизация (Code):** числа → `measurement` (`source='extracted'`); медзначимое (аллергены/состояния/травмы/препараты) → upsert с `confirmed=false` (бот подтвердит в диалоге); бытовые предпочтения → напрямую; `summary_delta` → слияние в `client_summary`; заметки → `coaching_note`.
- **Водяной знак:** обновляем `extraction_state.last_message_id`.
- **Архивация:** сообщения старше окна агента (напр. держим последние ~60 реплик/30 дней активными) копируем в `chat_history_archive` и удаляем из `n8n_chat_histories`. **ОСТОРОЖНО:** этой таблицей управляет узел `memoryPostgresChat`; удаление старого «из-под него» безопасно (он только дописывает и читает последние N по `contextWindowLength`), но порог архивации ОБЯЗАН быть ≥ окна агента. Требует явной проверки на живом прогоне.
- **Итог для агента:** контекст = последние N реплик (активная память) + `client_summary` + профиль + точечные запросы в ряды/коллекции. Не год чата.

## ОНБОРДИНГ (как наполняется профиль)

- **Не анкета.** Драйвер — NULL-поля `client_profile` в порядке приоритета: (1) основная цель + дисциплины; (2) база: рост/пол/дата рождения/вес/часовой пояс/единицы; (3) **безопасность**: травмы, состояния, аллергии; (4) предпочтения. Бот задаёт ОДИН недостающий пункт наибольшего приоритета за реплику, вплетая в разговор. `onboarding_done` ставится, когда закрыты приоритеты 1–3.
- **Верификация:** медзначимые факты (аллергия/травма/состояние/препарат) бот подтверждает ЯВНО («записал аллергию на орехи, верно?») → `confirmed=true`. Бытовые («люблю курицу») — без подтверждения.
- Профиль (со списком NULL-полей) инжектится в контекст агента, чтобы он знал, чего ещё не хватает.
- Таблица под онбординг не нужна — состояние держит сам профиль.

### Виды спорта фокус-группы → сид `activity_library`

Наполнить на старте (структура таблицы — под все виды, тегами закрываем безопасность):
падл-теннис, плавание, беговая дорожка, гребной тренажёр, велосипед, велотренажёр, ходьба,
футбол, силовой фитнес/тренажёрка, бег/циклика, эндуро/мото.

**Таксономия `load_tags`** (единая, работает на все виды — основа проверки исключений):
`axial` (осевая на позвоночник), `impact` (ударная), `knee_dominant` (коленно-доминантная),
`hip_hinge` (тазобедренный шарнир), `overhead`/`shoulder_load` (над головой / нагрузка на плечо),
`spinal_flexion` (сгибание позвоночника), `rotational` (ротационная), `lateral` (латеральная),
`grip` (хватовая), `sprint` (взрывная), `low_impact` (низкоударная).

Черновик разметки под сид (уточним при наполнении на подэтапе 1):
- падл-теннис → sport: `impact, lateral, rotational, shoulder_load, knee_dominant`
- плавание → cardio: `shoulder_load, low_impact`
- беговая дорожка / бег → cardio: `impact, knee_dominant`
- гребной тренажёр → cardio: `hip_hinge, spinal_flexion, shoulder_load, knee_dominant`
- велосипед / велотренажёр → cardio: `knee_dominant, low_impact`
- ходьба → cardio: `low_impact`
- футбол → sport: `impact, knee_dominant, lateral, rotational, sprint`
- эндуро/мото → sport: `grip, axial, impact` (стабилизация корпуса, вибронагрузка)
- силовой фитнес → strength: набор упражнений, теги на каждое (`axial, overhead, hip_hinge,
  knee_dominant, spinal_flexion, shoulder_load, ...`)
